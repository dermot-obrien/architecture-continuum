ServiceNow knowledge agent in Teams

A Copilot Studio agent that answers staff questions in Microsoft Teams from ServiceNow knowledge articles, set up the way Microsoft's current documentation recommends. The agent reuses the tenant's existing ServiceNow Knowledge Copilot connector connection, servicenowkb3, which indexes articles into Microsoft Graph with each article's ServiceNow read permissions carried across, so every answer is grounded only in articles the asking user could open in ServiceNow. The agent doesn't own that connection: it also feeds Microsoft Search and Microsoft 365 Copilot, and its configuration bounds what the agent can answer, so it is checked rather than set up here.

How a question is answered

  1. 1A member of the agent's security group asks a question in Teams.
  2. 2Teams passes the question with the user's Entra identity. With Authenticate with Microsoft the user isn't prompted to sign in.
  3. 3The agent queries the Graph index as that user, through the servicenowkb3 connection, which is its only knowledge source.
  4. 4The index returns only the articles whose ACL admits that user, as mapped from ServiceNow user criteria.
  5. 5The agent answers from those articles alone, with citations, or says it has no article and points to the portal.
  6. 6A citation opens the article in the ServiceNow Service Portal, where ServiceNow applies its own access check again.

How articles get there

This is what servicenowkb3 does if it is configured as recommended. Each step is something to confirm on the existing connection, not something this agent sets up.

  1. AThe connector signs in to ServiceNow with Federated Auth: an Entra-issued OIDC token for a machine integration user, so there's no secret to store or rotate.
  2. BIt crawls published, active articles in the chosen knowledge bases: changes every 15 minutes, a full crawl daily.
  3. CIn the Advanced flow it evaluates script-based user criteria through the scripted REST API, and picks up identity changes every 30 minutes.
  4. DIt writes each article into the Graph index with a read ACL built from its knowledge base and article user criteria.
  5. EServiceNow users are matched to Entra users by email against UPN or mail, so the ACL names real tenant identities.

Risks to watch

The architectural risk here is oversharing through permissions that don't survive the trip from ServiceNow into the index. Most of these failures are silent.

  • HR-scoped user criteria. Without an HR Core reader or admin role, the service account gets empty results instead of an error, and HR articles can be indexed as open to all.
  • Articles with no user criteria. They appear to everyone when glide.knowman.block_access_with_no_user_criteria is false.
  • Unreadable system properties. Without read access to sys_properties, the connector silently falls back to the most restrictive defaults, and articles go missing with no error.
  • Permission lag. The 15-minute crawl doesn't pick up knowledge-base-level permission changes. Those wait for the daily full crawl, unless identity sync is set up in the Advanced flow.
  • Identity mismatches. A ServiceNow user whose email matches no Entra UPN or mail gets no access, and a wrong match gets the wrong access.
  • Article content as untrusted input. Many people can contribute to a knowledge base. An article's text goes into the model's context, so contribution rights matter, even though the agent has no tools to misuse.
  • Confabulation and staleness. Answers can paraphrase wrongly or cite a since-retired article. The controls are evals on real questions with costed false positives, and citations shown to the user. See the evaluation plan.

What the test case shows about the standard The reach definitions need one clarification. An indexed enterprise source the agent retrieves from, trimmed to the user, is read, not knowledge, even though there are no tools. knowledge is for content loaded into the agent's own configuration. Separately, "untrusted content" should cover content many people can edit, not only content from outside.

F1 and its limits

  • F1 weighs both errors equally. It is the harmonic mean of precision and recall, 2PR / (P + R). Here a confident wrong answer costs far more than a polite "I can't find that", so F1 would reward trading one for the other.
  • Report F0.5 instead. F-beta is (1 + β²)PR / (β²P + R); β = 0.5 counts precision as more important than recall. Gate on the two floors, not on any single score: a better F-score bought by losing precision is a worse agent.
  • Name the positive class. "Precision" means nothing until the eval says whether a positive is an answer, a relevant article or a leak.
  • Balance the test set on purpose. If it holds only answerable questions, precision can't be measured honestly. Plan about 60% answerable questions across the chosen knowledge bases, 25% in-domain questions no article answers, and 15% out of scope.
  • Leakage is not on the curve. It is never traded for recall, so it has its own zero-tolerance eval.
  • Report intervals. 90% on 100 cases is roughly 83% to 95% at 95% confidence (Wilson). Zero failures in n probes bounds the rate only at about 3 in n, which is why the leakage eval needs about 300 probes.

Building and running the test set

  • Draw questions from real demand: ServiceNow portal searches with no click, and incident short descriptions. Knowledge base owners write the expected answers and article numbers.
  • Set up test users whose ServiceNow access differs (for example, one with HR access and one without). Plant canary phrases in restricted test articles indexed by servicenowkb3, and probe for them as the users who shouldn't see them.
  • Calibrate the LLM graders on at least 50 human-labelled cases before trusting their pass scores.
  • Run the gating evals before every promotion to production, after a model change, and weekly, because the knowledge bases change under the agent with every crawl.
  • Online, in production: watch the thumbs-down rate, the decline rate and the unanswered-question log. Feed unanswered questions to knowledge base owners as gaps; that is the agent's recall improving at the source.
  • Copilot Studio evaluations support only agents on No authentication or Authenticate with Microsoft, which is one more reason for the sign-in choice above.

Check in your tenant before building

  • That the agent returns Graph connector results in Teams under Authenticate with Microsoft. Microsoft's knowledge page says the ExternalItem.Read.All scope must be in the manual authentication setting, while its authentication page says to use Authenticate with Microsoft for the Teams and Microsoft 365 channel. If the scope isn't granted, use manual Entra ID authentication with Teams single sign-on.
  • Whether any user criteria use scripts: /api/now/table/user_criteria?advanced=true&sysparm_limit=1 on the instance. If any do, use the Advanced flow.
  • The service account's table access, with Microsoft's Copilot Connector Checker.
  • After the first full crawl, the indexed article count against the expected count, and the permissions of a few known restricted articles by sys_id.
  • Licensing: who has a Microsoft 365 Copilot licence, and the credit cap for everyone else.
  • Whether Microsoft Agent 365 is onboarded, so the agent can be governed as an Entra identity.
